# Evaluation

Three harnesses. The second one is the reason anyone should believe the rest.

## 1. Golden question set

~40 questions against a frozen snapshot, with answers verified by hand. Freeze the snapshot
first — pin a specific `osv/raw/PyPI/<stamp>/` prefix and a specific set of lockfiles, and
never regenerate answers against a moving graph.

Categories and rough weights:

    lookup         8    "is web-api affected by GHSA-x?"
    multi-hop      8    "which repos are exposed through urllib3?"
    aggregation    6    "how many CRITICAL advisories across all repos?"
    provenance     8    "why is web-api exposed to GHSA-x?"
    prose          5    "does GHSA-x need authentication to exploit?"
    unanswerable   5    no valid answer exists

**Build the ground truth by hand, from the lockfiles and the OSV records — never from the
graph.** An answer key generated by the system under test measures self-consistency, which is
not a thing anyone wants to know. It's slower this way. It's also the only version that means
anything, and 40 questions is a couple of hours.

**Grading.** Exact match where the answer is a set (advisory ids, repo names, a path). LLM
judge only for the prose category, and even there, grade against a hand-written reference
answer rather than asking a model whether the answer "seems good".

**Path questions grade on the path, not the endpoints.** `web-api -> fastapi -> starlette ->
anyio` and `web-api -> anyio` reach the same advisory, and only one of them is the answer to
"why".

### The unanswerable ones

The category that will get noticed. Five questions with no valid answer:

- about a repo that isn't in the graph
- about an advisory that doesn't exist
- requiring data you never ingested ("who reported this?")
- requiring a future fact ("will this be patched?")
- ambiguous between two repos with no disambiguation

Score **correct abstention**: did the agent say it couldn't determine this, or did it produce
a plausible sentence? Report it separately from accuracy. It's a safety metric — an agent
that scores 95% on the other 35 and fabricates all 5 of these is worse than one scoring 85%
and abstaining correctly, because the first one can't be trusted on any answer.

## 2. Delta correctness suite

The one nobody writes. Every delta type from `deltas.md`, asserted at all three layers.

    def test_withdrawn_advisory_is_fully_purged():
        load_snapshot("T0")
        assert agent.list_exposures("web-api")            # pre-state, via the agent
        apply_delta("T1")                                 # through the real pipeline
        assert not graph.node_exists(ADVISORY)            # graph
        assert not graph.edges_from(ADVISORY)             # no orphan edges
        assert not vector_index.contains(CHUNK_KEY)       # vectors
        assert not agent.list_exposures("web-api")        # agent
        assert "withdrawn" in agent.what_changed("T0")    # the log
        apply_delta("T1")                                 # again
        assert_no_change()                                # idempotency

Same shape for each type, with the assertion that makes that type distinctive:

    added              node, edges and chunks all appear; exposure now reported
    severity rescored  property changed AND zero Bedrock calls
    range narrowed     exactly the affected edges removed, advisory node still present
    range widened      new edges appear, existing ones untouched
    prose edited       exactly one chunk re-embedded, exactly one vector replaced
    withdrawn          the full purge above
    package upgraded   DEPENDS_ON subgraph rewritten, exposures recomputed

**"Exactly one" is the assertion worth the effort.** Count the Bedrock calls — a spy on the
client, or the registry's own miss counter. Anything that re-embeds an unchanged corpus still
produces correct answers, so nothing else in the suite catches it. That counter is the proof
the content-addressing works.

Run against a real graph, not a mock. A fake that implements your assumptions tests your
assumptions. If cost is the concern, this is the argument for a small graph you tear down —
see `runbook.md`.

## 3. Baseline comparison

The same 40 questions against plain vector RAG over advisory text: chunk everything, embed,
retrieve top-k, answer. No graph, no traversal.

Expected shape of the result, and say the expectation out loud *before* you run it:

    lookup         roughly ties        the advisory text names the package
    prose          baseline wins       it's a text question; the graph adds nothing
    aggregation    baseline collapses  counting isn't retrieval
    multi-hop      baseline collapses  the intermediate package appears in no document
    provenance     baseline near zero  the path exists in no text anywhere

Multi-hop and provenance are the interesting rows because the failure is structural, not a
tuning problem: no amount of retrieval finds a fact that was never written down. The chain
`web-api -> fastapi -> starlette -> anyio` exists only as an emergent property of four
separate lockfiles.

Build the baseline honestly. Same embedding model, same chunks, a reasonable k, the same
grading. A baseline you sabotaged proves nothing, and it's obvious to anyone reading.

If the baseline wins a row, publish that too. "The graph loses on prose questions" is a
finding, and it's the one that shows you understand which instrument answers which question.

## Reporting

One table in the README. Rows are categories, columns are graph agent / vector baseline,
cells are accuracy with n. Abstention gets its own row, marked as a safety metric rather than
an accuracy one.

Then the numbers that describe the delta work, which no accuracy table captures:

    deltas applied over the project             from the ingest log
    withdrawal fixtures replayed                from Track C
    Bedrock calls on an unchanged re-ingest      should be 0
    rebuild time from S3, cold                   minutes
    two rebuilds of one snapshot, checksums      identical

That last line is the one to lead with. "The graph is fully reconstructible from immutable
snapshots and two rebuilds are byte-identical" is a claim most people can't make about
anything they've built.

## Order

Golden set first, on the frozen snapshot, before the agent exists — the questions are
answerable in raw Cypher and writing them early tells you whether the model works. Delta
suite second, and it gates the agent: an agent over a graph that can't delete correctly is a
demo. Baseline last; it's the cheapest of the three and the first to cut.
